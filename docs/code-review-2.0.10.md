# 2.0.10 代码检查记录

## 范围

检查当前 Swift 应用的搜索、缓存、播放同步、窗口与渲染路径，结合整个 SwiftPM 工程的编译和回归测试。保留 `Legacy` 和第三方依赖的兼容实现；本次不以“全项目重写”替代针对问题的修复，也不将测试通过视为不存在其他问题的证明。

## 已处理

| 问题 | 原因与处理 |
| --- | --- |
| 来源顺序被标题匹配压过 | 原排序始终给准确标题额外 400 分。现在仅严格匹配保留该层级；宽松模式中可信变体按功能、来源排序。 |
| 仅逐字／仅双语时搜索拖延 | 原结束条件要求两项同时存在。现在各源完成有效查询轮次后回退；对已找到功能版本但仍在下载的情况，增加 8 秒补搜上限，新确认别名可重开机会，总预算 24 秒。 |
| 搜索状态反复遍历候选 | 满足条件的检查改为针对新增或重新评分的候选，保存已确认的可靠结果状态。 |
| 修改偏好仍出现旧排序 | 手动搜索记录配置标识；配置变化后不再混入旧评分结果。未完成缓存增加排序策略版本标识。已完成缓存和手动选择保留。 |
| 精简重试后结果逐渐增多 | 合并旧结果后仍按来源数量限制，保留该来源排序最好的 12 个版本；完整搜索不受此显示上限限制。 |
| 辅助文字含义不清晰 | 统一为枚举，集中定义标题、内容选择和稳定预留高度；补齐“翻译或下一句”。 |
| 播放时重复分析整首歌词 | 逐字与纯音乐标记在文档变化时更新；相同 UUID 的文档被替换时也会更新，避免只按 ID 缓存导致过期。 |
| 搜索实现集中在一个文件 | 将 `SourceConfiguration` 和 `SearchCollector` 拆出，各自维护排序策略和查询生命周期。 |

## 保留的资源边界

- 网络并发、请求重试和总搜索时间有上限；任务取消会传递给 HTTP 请求，结束时清理等待者和补搜任务。
- 临时缓存使用搜索令牌隔离，旧请求不得覆盖新的搜索或手动选择；继续使用已有 LRCX 文件与路径。
- 计时器保留暂停／不可见降频，悬浮窗隐藏时停止鼠标检测；逐字高亮仅更新当前行。
- 封面按歌曲身份复用并缩小到适合窗口的尺寸；歌词导入有 4 MB 文件大小限制，子进程等待在后台执行。
- 对来源返回异常、未完成下载和新别名延迟分别处理，未增加永久轮询或后台循环搜索。

## 验证

- 全工程 `swift test` 通过，测试工具报告 134 项；需要网络或特定环境的可选测试另行启用。
- 三首歌的独立联网验证均得到非 LRCLIB 的最终结果：中文逐字、英文双语、日文逐字双语；见本版发布说明。
- Release 构建无编译警告或错误；安装包签名校验通过，安装文件与构建产物哈希一致。
- 已安装应用中核对五种辅助文字选项，并实际选中“翻译或下一句”、检查设置页排版。
- 安装后一次 10 秒抽样约使用单核 0.4% CPU，RSS 约 188 MiB。此为当时使用状态的观测，不是与旧版在所有播放、拖动和分辨率场景下的全面性能对比。
